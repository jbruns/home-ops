# Startup Order is enforced by Host scripts, not by Compose

Compose `depends_on` only applies within one project and is ignored when dockerd restarts containers at boot. So: within a Stack we still declare healthchecks and `depends_on: service_healthy` (with `restart: true` from an app to its Datastore). Across Stacks, every Service carries a `startup-order` label: 0 edge, 1 Datastores and monitoring core, 2 Exposed Services, 3 sidecars and exporters. The startup-order Custom Component (in the Repo Tooling repo, ADR 0008) acts on these labels and is registered as TrueNAS Init/Shutdown Scripts. It is a shell script installed on the Host from a pinned release (`host/startup-order.pin`). We deliberately avoid OS-level changes such as systemd drop-ins: an appliance update can discard them, and they bypass the TrueNAS UI and API.

The boot-time script is the one that enforces the order. TrueNAS gives its shutdown task no ordering against `docker.service`, so the shutdown task is best-effort. It first records which containers are running, then stops them from level 3 down to 0. If it wins the race, `unless-stopped` keeps everything down until boot. If dockerd stops first, dockerd starts every container at once at boot. Either way, the post-init task waits for Docker and lets the restart-policy burst settle. It then stops anything at levels 2–3 and starts the targets (running now plus those recorded at shutdown) level by level, waiting for each to report healthy. When a level times out, it logs a warning and carries on. Containers that were stopped before shutdown stay stopped. After an unplanned power loss the post-init task still reorders, but anything that was down before the outage is not recovered.

The first verification reboot showed that dockerd had already stopped by the time the shutdown task ran, so the boot path did all the work. That reboot also showed that doco-cd, when dockerd restarts it at boot, deploys within seconds, before the post-init task can step in. A Service that crash-loops while its dependency is still down then fails that deploy ("has a restarting container"). Such a Service must wait for its dependency in its own entrypoint instead of exiting.
